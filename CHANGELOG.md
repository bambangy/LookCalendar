# Changelog

## 0.1.0

Initial release.

- `lkCalendar(el, opts)` orchestrator: toolbar, month/week/day/agenda views, built-in create/edit dialog
- `createCalendarStore()` — event/calendar data model with simple (daily/weekly/monthly) recurrence
- `createMonthView()`, `createTimeGridView()`, `createAgendaView()` — standalone view renderers
- `createEventForm()` — built-in, template-replaceable create/edit form on top of `@lookui/core`'s `lkForm`/`lkDate`/`lkDropdown`/`lkCheckbox`
- Drag-to-create, drag-to-move, resize (week/day), "+N more" overflow popover (month)
- `before*` guard hooks and `on*` notifications matching LookUI's own component conventions
- `newEventForm` / `editEventForm` options for a separate create vs. edit form template (a shared `eventForm` function template also receives `mode: 'create' | 'edit'`)
- `calendarStore` resolves each event's effective color: its own `color`, else its calendar's `color`, else the CSS default — recomputed on every read, so recoloring a calendar via `setCalendars()` updates its events immediately
- `multiDayStyle: 'continuous' | 'block'` (month view, default `'continuous'`): a multi-day event renders as one seamless bar across its days, or as a separate chip per day
- Fixed: the week/day time-grid header's `grid-template-columns` depended on a `--lkc-days` custom property that was only ever set on sibling elements, never the header itself or a shared ancestor — it rendered as a broken, overlapping header that could also swallow clicks meant for event chips underneath. Now set once on the view's container so every descendant inherits it.
- Fixed: the built-in form's start/end `lkDate` fields never showed the event's existing date — `lkDate` only writes its display text back into the trigger input when given `input: true` (or `displayFormat`), which `eventForm.js` wasn't passing.
- `autoColor` (default `true`, on `createCalendarStore()`/`lkCalendar()`): an event with no explicit color and no calendar color now gets a stable, deterministic color from a small built-in palette (hashed from its id) instead of every uncolored event collapsing onto the single CSS default. Pass `autoColor: false` to keep the old behavior.
- Full color-override tokens: every visual role (header, date numbers, time labels, today, drag-selection preview, marked days) now has its own `--lkc-*` token, so any one of them can be retargeted without side effects on the others — see `tokens/_calendar.scss` and the Theming docs.
- `markedDays` option (`lkCalendar` and each view) + `calendar.setMarkedDays()` / `view.setMarkedDays()`: color specific days independent of any event (weekends, public holidays, blackout dates). Rule shapes: a specific day, a yearly `MM-DD` day, a date range, a `weekday` list, or a matcher function. A marked day with no events still shows up in agenda view instead of disappearing. See `core/dayMarks.js`.
- `showNowLine` (week/day view, default `true`): a live line across today's column at the current time, repositioned every 30s.
- `businessHours` (week/day view): shades the hours/days outside `{ start, end, days }`.
- `hideWeekends` (month view): don't render Saturday/Sunday columns. Multi-day spans confined entirely to a hidden day are skipped; spans crossing a hidden day clip to the nearest visible one instead of disappearing.
- A calendar-icon button next to **Today** in the toolbar opens an `lkDate` picker to jump straight to any date.
- Fixed: drag-to-create/move/resize never called `preventDefault()`, so every drag also triggered the browser's native text/range selection — visibly, a selection highlight while dragging in month view; functionally, a stale `Selection` whose anchor node got removed by the next `render()` could leave the browser's selection machinery in a state that broke drag-to-select on the *next* attempt in week/day view. `dragCreate`/`dragMove`/`resize` now call `preventDefault()` once a gesture is confirmed underway, and the drag surfaces also get `user-select: none; touch-action: none` as a CSS-level backstop.
- Fixed: the toolbar's prev/next buttons only special-cased `'month'` and `'week'` — in agenda view they fell through to the generic ±1-day step, which barely shifted a 30-day-wide window (and the title, showing only "Month Year", often didn't change at all within the same month), making prev/next look like they didn't work. Agenda now pages by the full `agendaRangeDays` window, and its title shows the actual date range instead of just the month.
- Single-occurrence recurrence editing: `store.updateOccurrence(instance, patch, scope)` / `store.removeOccurrence(instance, scope)` (`scope`: `'this' | 'following' | 'all'`, default `'this'`) — editing/deleting one instance of a recurring event now works the way every mainstream calendar app does. `'this'` carves that date out of the series into a standalone exception event (the series gets an `exdate`); `'following'` ends the old series the day before and starts a new one from there, carrying the edit forward; `'all'` behaves like plain `update()`/`remove()` on the whole series. The built-in edit dialog, its delete button, and dragging a recurring occurrence to move/resize it all now ask this question before applying the change — a non-recurring event is unaffected and never shows the prompt.
- Event chips (month/week/day/agenda) now show the full start–end time range instead of just the start time, and a timed chip renders two lines — the time range (plus icon) on top, the title below. When a chip is too small for two lines (packed tightly in month view, or a short duration in week/day view), a CSS container query collapses it to one compact line showing only the time range and icon; hovering or focusing it pops it back to two lines on top of its neighbors (via `z-index`/negative margin), without reflowing the rest of the grid.
- Event icons: a per-event `icon` field, or a calendar-level `eventIcon(event)` template option (used as a fallback when an event sets no `icon` of its own) — see `core/eventIcon.js`. An icon spec can be a `@lookui/core` icon name, `{ lookui, size }`, `{ html }`, `{ url, alt }`, `{ emoji }`, a raw DOM node, or a function returning any of those.
- Fixed: a multi-day event in month view's `'continuous'` bar style rendered one full chip *per day* (repeating the title, and showing a cell-border seam at every day boundary it crossed). It's now a single chip, planted on the bar's start day and explicitly widened (`width: calc(N * 100% + ...)`) to visually span every day it crosses; the days in between just reserve the row slot with an invisible spacer. A `z-index` lifts the bar above the following days' own cell borders/backgrounds, which would otherwise repaint over the part of it that overflows past its own column — so there's no seam, and the title/time have the full multi-day width to breathe in instead of truncating to one day's worth of space.
- The built-in create/edit form (`createEventForm()`) now has Icon and Color fields by default: Icon is an `lkDropdown` over a curated `@lookui/core` icon-name list, Color an `lkColor` swatch+picker — both optional, both default to blank (inherit the event's calendar color / `autoColor`, no icon). `getValues()` now also returns `icon`/`color`. Editing an event whose `icon` isn't a plain icon name (an emoji/image/HTML/node icon set programmatically) leaves it untouched unless the user actually changes the icon field, since the built-in picker only edits the curated-name case.
- Documented the icon/two-line-chip feature across the docs site: a dedicated "Event chips" section with a live demo in [Views](docs/views.html#event-icons), an `eventIcon` entry (with a runnable example) in the API reference, and the new form fields in Customization's field-contract table.
- Complete API reference for every standalone-importable piece, not just `lkCalendar`: `docs/api-calendar-store.html`, `docs/api-month-view.html`, `docs/api-timegrid-view.html`, `docs/api-agenda-view.html`, `docs/api-event-form.html` — full options/properties/methods and runnable examples, same `LookDocs.render()` engine and format as `lkCalendar`'s own `api.html`. Cross-linked from the README, the Overview page's "modular by design" section, and a pill-switcher at the top of every API page. Fixed an i18n key bug surfaced while writing these (`eventForm.js`'s icon-picker placeholder was missing its `form.` prefix, so it silently fell back to the raw key).
- Keyboard accessibility: event chips (month/week/day) are now `role="button"`, focusable, and open the edit dialog on Enter/Space, with an `aria-label` built from the chip's own visible text (time + title). Month view's day grid is now a proper `role="grid"` with a roving `tabindex` — arrow keys move the focused day (Home/End jump to the row's edges), Enter/Space fires the same `onSelect` a drag-to-create does (`lkCalendar` opens the create dialog for it). Icon glyphs are marked `aria-hidden` wherever they sit next to a text label that already conveys the same information, so screen readers don't double-announce them. The toolbar, "+N more" popover, agenda rows and the built-in dialog's buttons were already plain `<button>`s and needed no changes.
- Timezone support: `opts.timezone` (an IANA zone, e.g. `'America/New_York'`) on `lkCalendar()`/`createCalendarStore()`/each view pins "today", every view's day/week/month boundaries, displayed times, and recurring events' cadence to that zone — independent of the viewer's own machine, which is what every date/time computation implicitly used before (two viewers in different zones could see a stored event on different calendar days, and a daily recurrence could drift off its intended local time across a DST transition). An event's own `event.timezone` overrides the calendar-level default for that event's own recurrence cadence. Built entirely on native `Intl` (`core/timezone.js`, re-exported as `calendarTimezone`) — no date library. Leaving `timezone` unset keeps every existing behavior exactly as it was; nothing changes for anyone not opting in.
- `.ics` (RFC 5545 / iCalendar) import/export: `exportICS(events, opts)` / `importICS(icsText)` (standalone, usable with no calendar/store) and `calendar.exportICS(opts?)` / `calendar.importICS(icsText)` on `lkCalendar` instances — interop with Google Calendar, Outlook and Apple Calendar via the same format they all read and write. A recurring event's `RRULE` maps to/from this library's own small recurrence model (daily/weekly/monthly, matching `core/recurrence.js`'s deliberate scope) rather than the full RFC 5545 recurrence grammar; a `VEVENT` whose `RRULE` doesn't fit (yearly, `BYSETPOS`, …) still imports as a single non-recurring event instead of being dropped. A zoned event's `TZID` round-trips through the new timezone support above. New `docs/api-ics.html` reference page and a live import/export demo in [Events & recurrence](docs/recurrence.html#ics-import-export).
- Clarified `docs/api-ics.html`: both functions only ever work with plain strings — `exportICS()` returns one (never a file/Blob/download), `importICS()` takes one (never reads a file itself) — with a full example `.ics` string for each direction, and runnable snippets for turning the export into a real downloadable file and reading an uploaded/dropped `.ics` file back in. The live demo in [Events & recurrence](docs/recurrence.html#ics-import-export) now has real "Download as a real .ics file" and "Upload a .ics file" buttons alongside the text-box round trip.
