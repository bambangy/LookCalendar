The event shape, the calendar data model, and LookCalendar's deliberately small recurrence engine.

Event shape

createCalendarStore() is the data layer — usable with no view at all if you want to render the calendar yourself. 

{
  id: string,            // auto-generated if omitted
  calendarId: string,    // default: 'default'
  title: string,
  start: Date,           // accepts Date | timestamp | 'YYYY-MM-DD' | any Date-parseable string
  end: Date,             // defaults to start + 30 minutes
  allDay: boolean,
  color: string | null,  // CSS color; overrides the calendar's color for this event
  editable: boolean,     // default true — false disables the built-in edit dialog and drag/resize
  recurrence: RecurrenceRule | null,
  data: any,             // anything you want to carry along
}

store.between(start, end) returns instances, not masters: a recurring event expands into one entry per occurrence, each carrying isRecurring: true, recurrenceId (unique per occurrence — use it for DOM keys) and masterId (the original event's id). Pass the whole instance (not just its id) to store.updateOccurrence()/store.removeOccurrence() — see below — or to plain store.update(instance.masterId, patch) if you always want to change the entire series.

Try it — editing one occurrence of a series

Click any occurrence of the recurring event below and save or delete it — the built-in dialog asks this event / this and following events / all events, the same choice every mainstream calendar app gives you. Dragging a recurring occurrence to move or resize it asks the same question.

Click an occurrence of "Daily sync" and save a change.

JavaScript — what the dialog calls underneath

// "This event" — carves this date out of the series into a standalone exception event;
// the series itself gets an exdate so it stops generating that slot.
store.updateOccurrence(instance, { title: 'Special agenda' }, 'this');

// "This and following events" — ends the old series the day before this occurrence and
// starts a new series here, carrying over the edited fields.
store.updateOccurrence(instance, { start: newStart, end: newEnd }, 'following');

// "All events" — same as store.update(instance.masterId, patch): changes the whole series.
store.updateOccurrence(instance, { color: '#ab47bc' }, 'all');

// Deleting works the same way:
store.removeOccurrence(instance, 'this');       // just this date
store.removeOccurrence(instance, 'following');  // this date and every later one
store.removeOccurrence(instance, 'all');        // the whole series

Try it — recurrence rule builder

Build a rule below and see it expand into concrete occurrences via the real expandRecurrence() function — the same one calendarStore.between() uses.

JavaScript

store.add({
  title: 'Daily standup',
  start: '2026-03-02T09:00',
  end: '2026-03-02T09:15',
  recurrence: { freq: 'weekly', byWeekday: [1, 2, 3, 4, 5], exdates: ['2026-03-06'] },
});

Try it — pinning a calendar (and a recurring event's cadence) to a timezone

By default every date is read back in whatever machine is running the code — "naive", in the sense that the same stored event can render a different wall-clock time (or even fall on a different calendar day) for two viewers in different zones, and a daily recurrence can drift off its intended local time across a DST transition. opts.timezone (an IANA name, e.g. 'America/New_York') pins "today", every view's day/week/month boundaries, displayed times, and recurring events' cadence to that zone instead — independent of the viewer's own machine. Switch the zone below: the same stored event (and the same daily recurrence) re-renders at the correct local time for whichever zone is selected, every time.

JavaScript

LookCalendar.lkCalendar('#calendar', {
  timezone: 'America/New_York',
  events: [{
    title: 'Daily standup', start: '2026-03-07T09:00', end: '2026-03-07T09:15',
    recurrence: { freq: 'daily', count: 10 },
  }],
});
// Every occurrence still reads 9:00 AM in New York after March 8's DST switch — the cadence is
// computed in that zone's wall clock, not a flat 24h added to the previous instant.

// An individual event can override the calendar's own zone for its own cadence:
store.add({ title: 'Tokyo kickoff', timezone: 'Asia/Tokyo', start, end, recurrence: { freq: 'weekly' } });

Zone-aware date math, if you're driving a view yourself

import { calendarTimezone as tz } from '@lookui/calendar';

tz.zonedParts(someInstant, 'Europe/London');      // -> { year, month, day, hour, minute, second }
tz.toZonedDate({ year: 2026, month: 3, day: 2, hour: 9 }, 'Europe/London'); // -> the correct instant
tz.startOfDayInZone(someInstant, 'Europe/London');
tz.addDaysInZone(someInstant, 1, 'Europe/London'); // DST-safe
tz.listTimeZones();                                // every IANA zone this engine knows
tz.systemTimeZone();                                // the viewer's own zone, e.g. 'Asia/Jakarta'

Try it — import/export .ics (interop with Google Calendar, Outlook, Apple Calendar)

Both functions work with plain strings — exportICS() returns the .ics file's text as a string (it doesn't download anything itself), and importICS() takes that same kind of string (however you got it — a file, a paste, a fetch) and returns plain events. exportICS(events, opts) / importICS(ics) read and write the same RFC 5545 format every major calendar app does, so a file this library exports opens correctly there, and a file downloaded from any of them imports back in. See the full exportICS / importICS reference for exactly what that string looks like both directions, and the (deliberately small, matching this page's own recurrence model) RRULE mapping.

The box below is just so you can see the string — exportICS()/importICS() never touch a textarea, a file, or the DOM themselves.

Add/edit an event above, then try exporting and re-importing it.

JavaScript — what each button above actually calls

// "Export" — exportICS() returns a string. That's it — nothing is downloaded yet.
const ics = calendar.exportICS();                  // or: exportICS(store.all(), opts)

// "Download as a real .ics file" — turning that string into a file your browser saves.
const blob = new Blob([ics], { type: 'text/calendar;charset=utf-8' });
const url = URL.createObjectURL(blob);
const a = Object.assign(document.createElement('a'), { href: url, download: 'calendar.ics' });
a.click();
URL.revokeObjectURL(url);

// "Upload a .ics file" — reading a File the user picked into the string importICS() wants.
fileInput.addEventListener('change', async () => {
  const text = await fileInput.files[0].text();     // a string
  const added = calendar.importICS(text);            // or: importICS(text) -> add each yourself
});

// "Import from the text box" — same call, fed from the textarea instead of a file.
const added = calendar.importICS(icsTextFromBox);

Reference — recurrence rule

FieldTypeNotes
freq'daily' | 'weekly' | 'monthly'required
intervalnumberevery N days/weeks/months, default 1
byWeekdaynumber[]0 (Sun)…6 (Sat); weekly only — defaults to the start date's weekday
untilDate | stringstop after this date (inclusive)
countnumberstop after N occurrences
exdates(Date | string)[]specific occurrences to skip

This is a deliberately small engine, not a full RRULE parser. If you need full iCalendar RRULE support, expand your own events with a dedicated RRULE library and pass the already-expanded instances straight to a view — the render(date, instances, calendars) contract doesn't require calendarStore at all.
